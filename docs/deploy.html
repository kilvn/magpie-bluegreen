三分钟起步

💡 不想手写配置？直接下载仓库预设的样例文件

GitHub 仓库已内置开箱即用的完整模板目录（含 docker-compose.yml、env.example、nginx.conf 反代及客户端片段）：

📂 浏览 examples/ 完整样例目录 → 📄 直接下载 docker-compose.yml

  1. 建目录

    整个部署就是一个自包含的目录，备份、迁移、删除都只涉及它。

    mkdir -p /srv/magpie/data
cd /srv/magpie
    # 部署后的目录结构 /srv/magpie ├── docker-compose.yml ├── .env # 密钥与域名，不进版本库 └── data/ # 挂到容器的 /config，所有状态都在这里 ├── magpie/ # 供应商、密钥、插件配置 ├── cache/ # 模型缓存、npm/uv 缓存 └── home/

  2. 写 compose 文件

    cat > /srv/magpie/docker-compose.yml <<'YAML'
name: magpie

services:
  magpie:
    image: ghcr.io/yetone/magpie:latest
    container_name: magpie
    restart: always
    command: ["web", "--addr", "0.0.0.0:3430", "--no-open"]

    ports:
      # 3430：控制台 + /v1 网关接口（对外只需这一个）
      - "127.0.0.1:3430:3430"
      # 3425：独立网关端口（可选，不用可以删掉）
      - "127.0.0.1:3425:3425"

    volumes:
      - ./data:/config

    environment:
      MAGPIE_ADDR: 0.0.0.0:3425
      MAGPIE_PUBLIC_URL: ${MAGPIE_PUBLIC_URL:-}
      MAGPIE_WEB_KEY: ${MAGPIE_WEB_KEY:-}
      TZ: ${TZ:-Asia/Shanghai}
      HOME: /config/home
      XDG_CONFIG_HOME: /config
      XDG_CACHE_HOME: /config/cache
      XDG_DATA_HOME: /config/data
      XDG_STATE_HOME: /config/state

    healthcheck:
      test: ["CMD", "/magpie", "healthcheck"]
      interval: 30s
      timeout: 5s
      start_period: 10s
      retries: 3
YAML

    为什么绑 127.0.0.1。容器只监听本机回环，公网碰不到，所有外部流量必须经过你的反代（下一节）。想直接 IP 访问就把 127.0.0.1: 去掉——但那样会绕过反代的限流与 WAF。

  3. 写 .env

    先生成控制台密钥。密钥必须至少 16 个字符，否则容器启动即退出并反复重启（日志：MAGPIE_WEB_KEY is 10 characters; it needs at least 16）。

    # 控制台访问密钥，拼在 URL 后面 ?k=...
# 32 位十六进制 = 32 字符，稳过下限
openssl rand -hex 16
    cat > /srv/magpie/.env <<'ENV'
# 控制台密钥，至少 16 字符；留空则每次启动随机生成（重启后旧链接失效）
MAGPIE_WEB_KEY=把上面生成的 32 位十六进制粘这里

# 对外域名，用于控制台里生成的回调与展示链接；纯内网可留空
MAGPIE_PUBLIC_URL=https://gw.example.com

TZ=Asia/Shanghai
ENV

chmod 600 /srv/magpie/.env

    两个后果都要注意：密钥留空 → 每次重建都换一把，旧链接全部失效；密钥不足 16 字符 → 容器直接起不来，而且会无限重启，compose ps 里只看到 Restarting，很容易误判成镜像问题。

    网关调用密钥（sk-...）不在这里配，由 magpie 在控制台里生成。

  4. 修数据目录属主

    镜像以 uid 65532（nonroot） 运行。不做这一步，容器会持续报 mkdir /config/magpie: permission denied，所有配置都存不下来。

    chown -R 65532:65532 /srv/magpie/data
stat -c '%u:%g %n' /srv/magpie/data   # 应输出 65532:65532

    健康检查不碰磁盘，所以目录权限错了容器照样显示 healthy。看到「起来了但存不住配置」，先查这里。

  5. 启动

    cd /srv/magpie
docker compose up -d
docker compose ps

    期望看到 magpie ... (healthy)。等健康检查通过（约 10–30 秒）：

    # 401 = 进程活着但需要鉴权，这是正常结果
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3430/api/health

首次进入控制台

控制台地址形如：

http://127.0.0.1:3430/?k=你的 MAGPIE_WEB_KEY

三件事按顺序做：

  1. 添加供应商：填 API Key 与 Base URL，magpie 会拉取该家的模型列表。
  2. 建分组：把模型按用途归类（如 coding、chat），分组名就是调用时的模型名 group/coding。
  3. 生成调用密钥：在「调用方 / API Keys」里新建，得到的 sk-... 就是客户端要用的 key。

验证网关真的能转发：

curl -s http://127.0.0.1:3430/v1/models \
  -H "Authorization: Bearer sk-你的调用密钥" | head -c 400

# 实际对话
curl -s http://127.0.0.1:3430/v1/chat/completions \
  -H "Authorization: Bearer sk-你的调用密钥" \
  -H "Content-Type: application/json" \
  -d '{"model":"group/coding","messages":[{"role":"user","content":"hi"}]}'

配反向代理（含流式要点）

magpie 的响应大量是 SSE 流式输出，反代配错的表现是前端一直转圈、最后超时，而不是报错。必须关掉缓冲。

server {
    listen 443 ssl http2;
    server_name gw.example.com;

    ssl_certificate     /etc/ssl/gw.example.com.pem;
    ssl_certificate_key /etc/ssl/gw.example.com.key;

    client_max_body_size 32m;

    location / {
        proxy_pass http://127.0.0.1:3430;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # —— 流式三件套，缺一不可 ——
        proxy_buffering off;
        proxy_cache     off;
        gzip            off;

        # 长推理可能跑几分钟，默认 60s 会直接断
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        send_timeout       3600s;
    }
}
如果反代在容器里

反代容器访问不到宿主机的 127.0.0.1。两种写法：把 magpie 加入同一个 docker 网络后用服务名；或让 magpie 绑到 docker 网桥网关 IP（如 172.17.0.1:3430），反代再指向它。

如果前面还有 CDN

Cloudflare 之类的 CDN 也需要关掉对 /v1 的缓冲与缓存，否则流式照样被整段攒住。同时确认其读超时足够长。

可选：让 MCP 资源库能用

magpie 的「资源库」用 npx / uvx 拉起 MCP 服务。官方镜像基于 Debian 12，除 /magpie 外没有任何运行时，所以不装这一节，添加资源库时会报 notfound。

不用 MCP 就整节跳过——网关的核心转发能力不依赖它。

准备运行时目录

mkdir -p /srv/magpie/runtime/{node,uv,git}

# Node 22（需要 glibc ≥ 2.28）
curl -fsSL https://nodejs.org/dist/latest-v22.x/node-v22.23.4-linux-arm64.tar.xz \
  | tar -xJ -C /srv/magpie/runtime/node --strip-components=1

# uv / uvx（静态二进制）
curl -fsSL https://github.com/astral-sh/uv/releases/latest/download/uv-aarch64-unknown-linux-gnu.tar.gz \
  | tar -xz -C /srv/magpie/runtime/uv --strip-components=1

amd64 机器把 arm64 / aarch64 换成 x64 / x86_64。git 只有特定资源库条目需要，可选。

挂进容器

# docker-compose.yml 的 volumes 增加
    volumes:
      - ./data:/config
      - ./runtime/node:/opt/node:ro
      - ./runtime/uv:/opt/uv:ro

# environment 增加 PATH 与缓存位置
      PATH: /opt/node/bin:/opt/uv:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
      npm_config_cache: /config/cache/npm
      UV_CACHE_DIR: /config/cache/uv
      UV_PYTHON_INSTALL_DIR: /config/cache/uv-python

缓存指向 /config/cache，随数据目录持久化，容器重建不会重新下载。运行时挂载用 :ro，多个 magpie 实例可以共享同一份。

验证：

docker compose exec magpie sh -c 'node -v; npx -v; uv --version; uvx --version'

升级策略

magpie 迭代很频繁，一天可能发布十几次。手动 compose pull && up -d 的问题是会掐断正在进行的流式请求和长推理——而且被掐断的请求不会留下用量记录，看起来像「莫名少了几次调用」。

推荐：用蓝绿切换脚本升级

一个 shell 脚本自动完成：拉新镜像 → 起临时容器 → 健康检查 + 真实业务探测 → 反代切流量 → 旧容器按连接数退役 → 原位重建 → 切回 → 删旧镜像。任何一步失败自动回滚，客户端全程无感。

兼容两种部署形态：compose 模式（检测到 compose 标签，走 compose up --force-recreate）与 docker 模式（无标签，从容器反推端口/环境/挂载后用 docker run 重建）。也带交互菜单。

github.com/kilvn/magpie-bluegreen → 
# 下载
curl -fsSLO https://raw.githubusercontent.com/kilvn/magpie-bluegreen/master/magpie.sh
chmod +x magpie.sh

# 只读看它识别成什么（不改任何东西）
sudo ./magpie.sh --status

# 走一次完整升级
sudo ./magpie.sh --upgrade

# 交互菜单：装定时任务、看日志、清理对话
sudo ./magpie.sh

它需要的配置极少，其余全自动探测：

cat > /etc/magpie-upgrade.env <<'ENV'
CONTAINER=magpie
DATA_DIR=/srv/magpie/data
RUNTIME_DIR=/srv/magpie/runtime
# 配了 VHOST 才是零停机模式；不配则退化为「先验证后重建」，窗口 1–2 秒
VHOST=/etc/nginx/conf.d/gw.example.com.conf
PUBLIC_HOST=gw.example.com
ENV

不装脚本的话，手动升级

cd /srv/magpie
docker compose pull
docker compose up -d --wait      # --wait 等健康检查通过才返回
docker image prune -f            # 清掉旧镜像层

适合个人低流量部署。如果你有长连接客户端或自动化 Agent 在跑，会感知到中断。

运维速查

操作命令
看状态docker compose ps
看日志docker compose logs -f --tail=100 magpie
重启docker compose restart magpie
健康探测curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3430/api/health
进容器docker compose exec magpie sh
备份tar czf magpie-$(date +%F).tar.gz -C /srv magpie/data
升级镜像docker compose pull && docker compose up -d --wait
彻底卸载docker compose down 后按需删除 /srv/magpie

备份只有一条：整个 data/ 目录。供应商、密钥、分组、插件、对话记录、用量统计全在里面。恢复时把它放回原位、修好属主，compose up -d 就回来了。

常见问题

容器 healthy 但配置存不住。数据目录属主不是 65532:65532。健康检查不碰磁盘，所以显示正常。

控制台链接每次重启都变。MAGPIE_WEB_KEY 没固定，每次启动随机生成。写进 .env。

compose ps 一直显示 Restarting。先看日志 docker compose logs magpie | tail -20。最常见是 MAGPIE_WEB_KEY 少于 16 字符（it needs at least 16），其次是数据目录属主不对。两者都不会体现在健康检查里。

流式输出卡住不动。反代开了 proxy_buffering。关掉它、proxy_cache 和 gzip，并把读超时提到 3600s。

调用返回 401。三种可能：key 没用 Bearer 前缀；key 是在别的实例上生成的；访问的是 3430 但路径少写了 /v1。

模型名报不存在。magpie 对外暴露的名字是分组名，格式 group/<分组名>，不是上游原始模型名。

端口已被占用。先确认没有另一个 magpie 在跑：docker ps -a --filter name=magpie，以及 ss -tlnp | grep -E '3430|3425'。

资源库提示 notfound。容器里没有 npx/uvx，见「可选：让 MCP 资源库能用」。

官方镜像 ghcr.io/yetone/magpie，容器内以 uid 65532 运行，控制台与网关同端口 3430（/v1）。
